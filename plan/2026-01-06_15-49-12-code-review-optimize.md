# Plan: 全面审查仓库代码并提出优化方案

🎯 任务概述
本仓库为全栈应用：FastAPI 后端（含 PostgreSQL/Redis 依赖）、React+TypeScript 前端，以及用于导入/处理数据的 ETL 脚本。
目标是在不破坏既有行为与数据格式的前提下，系统性审查代码质量/性能/安全/可维护性，并输出“问题清单 + 分批可落地修复方案 + 验证步骤”。

📋 执行计划
1. 仓库画像与运行基线：梳理 README/现有启动方式/环境变量/依赖与目录约定，确定“最小可运行路径”（后端/前端/ETL）作为后续回归基线。
2. 建立审查清单与输出格式：定义检查维度（正确性/安全/性能/可复现/可维护/可测试/文档一致性）与问题分级（P0/P1/P2），统一记录模板，便于追踪与复盘。
3. 使用 augment 建立索引式走查路线：围绕“入口→路由→业务逻辑→数据访问→缓存→外部 IO/ETL→前端调用链”设计检索问题集，定位关键路径与高风险点（硬编码路径、慢循环、未校验输入、裸 SQL 等）。
4. 后端静态审查（FastAPI）：重点检查配置管理、依赖注入、数据库会话/事务边界、Pydantic 校验、错误处理与日志、鉴权/速率限制/CORS/Trusted Hosts、安全默认值与敏感信息处理。
5. ETL/数据导入审查：重点检查批处理写入、幂等性与断点续传、内存占用（流式读取 vs 全量加载）、异常恢复、数据校验与约束（索引/唯一键）以及对大文件的性能路径。
6. 前端静态审查（React+TS）：重点检查 API 调用封装与错误态、类型安全与边界处理、性能（渲染/大数据可视化组件）、安全（XSS/URL 参数）、可访问性与构建产物体积。
7. 基础设施与部署审查：检查 docker-compose/Dockerfile/ENV 示例与“安全默认值”（只读文件系统、cap_drop、no-new-privileges 等），并核对文档与实际一致性；识别本地开发与生产配置差异。
8. 可行性评估与优先级排序：对候选修改点用 sequential-thinking 做影响面/收益/风险评估，形成分批实施顺序（先 P0 安全与稳定性，再性能与体验，最后重构与风格统一）。
9. 分批实施与验证：每批次限定改动范围（模块/文件数/风险级别），涉及第三方库用 context7 查询权威用法；同步补齐或调整测试（单测/集成/E2E）与最小回归脚本，确保无回归。
10. 交付与回滚：输出审查报告（问题清单、修复摘要、验证记录、未决项与后续建议），并为每批变更提供回滚策略（可逆改动优先、必要时 feature flag/配置开关）。

⚠️ 风险与注意事项
- 结果可复现性风险：科研/数据处理逻辑的“看似重构”可能改变输出；需要先建立基线样例与对比方法（hash/行数/统计指标）。
- 环境与依赖风险：前后端与数据库/缓存联动较多，且可能依赖大体量数据；建议优先在最小样例数据下完成回归，再扩展到全量数据。
- 兼容性风险：接口/Schema/SQL 结构变更需谨慎；未获确认前避免破坏性升级依赖或改动 API 形状。
- 耗时风险：全量构建、E2E、数据导入可能耗时较长；执行前需明确验收标准与可接受耗时窗口。
