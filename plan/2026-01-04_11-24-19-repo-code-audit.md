# Plan: 全仓代码审查与改进（前后端/ETL/CI）

🎯 任务概述
本任务目标是对当前目录的代码做一次“可落地”的全面审查：产出可追踪的问题清单与按优先级排序的改进方案，并在用户确认范围后进入 Execute 阶段逐项落地，确保 GitHub Actions 全绿。

## ✅ 需要确认的关键问题（进入 Execute 前）
1. 本轮“可以改”的范围：仅修 bug/性能/可维护性，还是允许做 API/行为调整？
2. 是否允许升级依赖（npm/pip），以及升级的上限（patch/minor/major）？
3. 性能优化的验收偏好：更关注首屏、交互流畅、还是后端吞吐/延迟？是否有目标阈值？
4. 优先模块：前端（Network/IGV/Epigenomics） vs 后端 API vs ETL 数据管道，哪个优先？
5. 是否允许新增/调整测试（unit/e2e），以及 CI 运行时长是否有限制？
6. 是否允许对数据文件/索引做结构调整（可能影响部署与存储）？

## 📋 执行计划
1. **冻结范围与验收标准**：明确“必须修/可选修/不做”的边界；记录当前 main 的 CI 状态与关键入口。
2. **使用 augment 建立全局索引**：定位入口文件、核心路由、数据模型、关键页面、重复工具函数、可能的性能热点；形成“代码地图”。
3. **静态与依赖审查**：分别对前端/后端运行最小静态检查（typecheck、lint/ruff、mypy 如有）；列出依赖风险（过期/漏洞/重复依赖）。
4. **后端审查（API/数据访问/缓存/异常）**：逐路由检查参数校验、错误处理、缓存策略、分页/截断、N+1 风险、日志与可观测性。
5. **前端审查（性能/状态/渲染/交互）**：重点检查大数据渲染（Cytoscape/IGV/ECharts）、React Query 缓存与重试、组件重渲染、事件监听与内存泄漏、错误提示/降级。
6. **ETL/数据一致性审查**：检查数据生成脚本的可重复性、输入输出契约、增量/全量模式、失败恢复、数据版本与校验。
7. **归纳问题清单并打分排序**：用 Impact × Confidence / Effort 形成 Top 5 必改 + Top 10 可选；每项包含定位证据、建议方案、验证步骤、回滚策略。
8. **制定落地节奏（Execute 计划）**：按“单点小步提交”推进；每项改动绑定最小验证与 CI 检查；更新文档（docs/README）记录行为变化与运维指引。

## 🧪 验收标准（本轮）
- 形成一份可追踪的审查报告：每个问题有 `file:line`、优先级、修复建议、验证方式。
- 在用户确认后，按优先级落地至少 Top 1~3 项改进，并确保 GitHub Actions（Tests/Security Audit 等）成功。
- 不做“无关格式化/大重构”；每个改动都可独立回滚（单独 commit/PR）。

## ⚠️ 风险与注意事项
- 审查容易发散：必须用“问题清单 + 打分”控制范围，避免无休止重构。
- 依赖升级与数据结构调整风险高：默认只做低风险修复；高风险项单列为后续方案。
- CI 可能存在历史不稳定：若出现与本次无关的失败，停止扩散修复并记录。

## 🔁 回滚/止损策略
- 每个问题独立 commit；必要时使用 `git revert <sha>` 快速回滚。
- 对可能影响行为的改动，优先保持向后兼容或增加开关（需用户确认）。
