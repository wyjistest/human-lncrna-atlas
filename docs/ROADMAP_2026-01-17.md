# 未来 1–2 周路线图（可执行）

目标：在不破坏现有 API/数据格式的前提下，把“可持续开发能力”做扎实（CI 可重复、文档一致、问题可追踪），并为下一阶段的数据与可视化迭代打好底座。

## 1) 本周（1 周）优先级：稳定性与可重复性

### 1.1 CI 与本地一致性（P0）
- 以 GitHub Actions 为准建立“本地可一键复刻”的检查入口：`./scripts/run-tests.sh ci`。
- 明确不在 CI 中执行的部分：E2E（需服务/数据）、security-audit（依赖漏洞可能需要单独迭代）。
- 验收标准：本地 `ci` 通过后，push 触发的 `Tests` 工作流成功（`gh run list` 可见成功记录）。

### 1.2 文档一致性回归（P0）
- 统一文档中的启动入口与命令示例（尤其是 `python3`、`uvicorn main:app`、端口与环境变量）。
- 为“最小可运行路径”补一段明确说明：无数据/无 DB 情况下能跑哪些检查（lint/unit/import/syntax）。

### 1.3 代码库卫生（P1）
- 通过 `.editorconfig` 固化行尾/空白策略，降低 CRLF/LF 混用导致的噪音 diff。
- 仅做“规则落地”，不进行全仓库重写行尾（避免超大 diff）。

## 2) 下周（2 周）方向：性能、可观测与数据迭代

### 2.1 性能与缓存（P1）
- 为高频 API 增加可观测性闭环：命中率、回源耗时、热点 key 分布（不引入新依赖为前提）。
- 对“列表/批量”接口做分页与缓存策略复核，确保大请求下也能稳定退化（限流/超时/错误信息脱敏）。

### 2.2 安全与依赖审计（P1）
- 关注 `security-audit` 的真实失败项：优先通过升级/约束修复高危依赖（high/critical）。
- 不以“忽略漏洞”作为默认策略；确需例外时在文档中记录原因与替代方案。

### 2.3 数据与 ETL（P2）
- 对外部下载/导入链路补“可选校验”（checksum/最小尺寸/行数范围）避免静默损坏。
- 形成最小样例数据集与对比基线（hash/统计摘要），为后续重构提供回归锚点。

## 3) 风险与依赖

- 依赖安全审计可能触发“牵一发而动全身”的升级链：建议按 P0（能自动修）→P1（需改代码）分批推进。
- E2E/全量数据导入耗时与环境依赖强：默认只在时间窗口允许时执行，并提前约定验收范围。
